# 设计说明

buptwc 是面向单个账号的 Linux 命令行程序：从强智课表计算监控窗口，在窗口内查询 uCloud，将新增互动课堂通知写入本地发送队列，再投递到企业微信群机器人。

课表负责调度，平台通知负责触发提醒。两者不通过课程名称或平台课程 ID 做关联。当前没有 Web 服务、自动签到或多账号并发运行功能。

使用方法见 [使用指南](usage.md)，代码导航和测试见 [开发指南](development.md)。本文描述当前实现及其边界。

## 数据流

```text
强智 XLS → 解码与校验 → 保存课表 → 展开课程日期 → 合并监控窗口
                                                        ↓
CAS 登录 → 本地会话 → 完整查询 uCloud 通知 → SQLite 事务 → 发送队列 → 企业微信
```

启动 `run` 时加载课表和配置，生成本次进程使用的全部窗口。运行期间不热更新配置或课表。查询和发送在同一个循环中串行执行，循环按下一次查询、队列重试或窗口边界等待。

队列处理不受课程窗口限制。监控器用 `poll.timeout` 限制一轮完整通知读取的总耗时，默认 15 秒；超时结果不提交。每批发送最多处理 10 个任务，并共用 `notify.timeout` 的时间预算，默认 10 秒。尚未开始的任务留到下一轮；已尝试但失败的任务按重试策略处理。请求和队列处理时间仍会影响下一次查询的实际时间。

## 课表与时间窗口

文件解码将 BIFF XLS 或 HTML 表格转换为网格，课程解析再生成包含名称、教师、地点、周次、星期和节次的排课记录。整个文件校验及窗口展开成功后才替换数据库中的课表。

第一教学周的周一和节次时间由配置提供。课程按周次、星期展开为具体日期，然后按配置顺序应用取消、移动和新增规则。未匹配到课程的取消或移动规则视为配置错误。

`course` 模式覆盖整段课程，包括中间课间；`period` 模式分别生成每小节窗口。窗口加上课前、课后偏移后合并，以左闭右开区间 `[开始, 结束)` 判断是否允许查询。

## 通知读取与识别

CAS 登录取得 Ticket，随后调用 `/ykt-basics/oauth/token`，以 `grant_type=third` 交换会话。会话包含访问 Token、用户 ID 和过期时间；当前不使用 Refresh Token 自动续期。

通知请求为 `POST /ykt-basics/api/inform/news/list`，查询参数包括收件人 ID、页码和页大小，请求体为空。客户端检查 HTTP 状态、业务状态、记录结构和分页信息。通知 ID 按字符串处理，避免大整数精度损失。

分页顺序尚未确认，因此遇到已见 ID 不提前结束。总量变化、页数不符、记录缺失或重复 ID 会使整轮扫描失败。只有完整扫描结果才进入存储事务。

提醒条件为三个字段同时匹配：

```text
type == "互动课堂"
newsModel == "chat"
newsUrl == "TO_CLASS"
```

`isRead` 不参与判定。`TO_CLASS` 是平台路由标记，消息中不将它转换为链接。

## 基线、去重与发送

SQLite 保存四类数据：

| 数据 | 用途 |
| --- | --- |
| `timetable` | 当前课表及导入时间 |
| `accounts` | 账号是否已建立基线、最近完整扫描时间 |
| `seen` | 按账号和通知 ID 去重 |
| `outbox` | 消息内容、有效期、重试时间、次数和状态 |

每个账号的首次完整扫描只建立基线，不创建发送任务。后续扫描在同一个事务内插入已见记录和符合条件的发送任务。事务失败时两者都回滚，下一次完整扫描可重新处理该通知。

相同 ID 的内容更新不会触发第二次提醒。切换账号不会发送旧账号的队列；退出登录只删除会话，不删除数据库。

发送任务的状态变化为：

```text
pending ── 企业微信 errcode=0 ──→ sent
   │
   ├── 失败且仍可重试 ─────────→ pending（更新次数及重试时间）
   ├── 达到尝试上限 ───────────→ failed
   └── 到期或重试将越过有效期 ─→ expired
```

通知时间优先使用 `newsCopyTime`，其次使用 `createTime`；均无法解析时，使用完整扫描成功后的观察时间。未来时间被截到观察时间。此时间加上 `notify.ttl` 得到发送截止时间。

企业微信只有返回 `errcode=0` 才视为发送成功。失败采用有上限的指数退避；队列持久化，使进程重启后能继续处理仍有效的任务。会话失效后停止平台查询，当前账号队列处理结束后退出。

## 设计取舍

| 选择 | 原因与代价 |
| --- | --- |
| 单进程串行循环 | 便于维持请求顺序和状态；慢请求会延迟其他工作 |
| SQLite 事务与发送队列 | 保持去重和入队一致，支持重启恢复；需要维护本地数据库 |
| 课表决定查询窗口 | 避免依赖未确认的课程 ID 映射；窗口内所有匹配通知都可能触发提醒 |
| 首次扫描建立基线 | 避免启动时推送历史；首次扫描中刚出现的通知也会被跳过 |
| 完整读取分页 | 不依赖服务端排序；通知量越大，单轮查询耗时越长 |
| 有效期和有限重试 | 限制迟到提醒和失败重试；不保证每个任务最终送达 |

发送到企业微信与更新 SQLite 无法成为同一个事务。若企业微信已收到消息，但响应丢失，或者程序在保存成功状态前退出，后续重试可能重复投递。当前既不承诺恰好一次投递，也不承诺最终一定送达。

## 本地状态与进程生命周期

默认配置通过用户配置目录定位，Linux 下遵循 `XDG_CONFIG_HOME`，未设置时使用 `~/.config/buptwc/config.toml`。`--config` 显式覆盖路径，不搜索当前目录。`init` 使用嵌入模板，以独占创建方式写入文件，避免覆盖用户配置；学期日期必须由用户填写。

配置文件权限为 `0600`。默认状态存放在配置目录的 `state/` 子目录，状态目录权限为 `0700`，会话文件为 `0600`。密码不落盘，Webhook 通过环境变量传入。HTTP 错误包装避免输出请求 URL、Token 或服务端原始响应。

需要独占访问的命令通过 Linux 文件锁协调；`status`、`courses`、`plan` 可在监控进程运行期间查询数据库。数据库使用 WAL，已有且版本匹配的数据库不重复执行建表事务。

CLI 将已分类的配置、会话和缺少课表等错误映射为退出码 `2`，其他返回错误为 `1`。随附的 systemd 服务对退出码 `2` 停止自动重启。该分类不是对所有永久故障的完整识别，其他错误仍需结合日志判断。

## 外部协议的未验证部分

当前代码和本地模拟测试不能确认以下平台行为：

- 登录 `user_id` 与通知收件人 `newsCopyPersonId` 是否始终一致。
- 不同角色需要的 `Identity`、`Tenant-Id` 请求头。
- 分页是否具有快照一致性：即使总量不变，分页期间记录被替换也可能漏过当前扫描。
- `newsCopyTime`、`createTime` 的实际语义，以及提醒有效期是否合适。
- 真实 CAS 验证码流程、会话寿命和 Refresh Token 协议。

协议参考：[bupt-ucloud-tool](https://github.com/OneZ3r0/bupt-ucloud-tool)、[bupt-auth](https://github.com/byrdocs/bupt-auth)。平台联调结果应更新到本文对应约束，不能仅以本地测试通过作为兼容性结论。
